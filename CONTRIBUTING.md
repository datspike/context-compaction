# Вклад в проект

## Перед изменениями

- Обсудите изменение в issue, если оно меняет публичный контракт расширения.
- Не меняйте Pi core и не добавляйте private runtime bridges.
- Не добавляйте секреты, локальные конфиги, `node_modules` и временные артефакты.

## Проверка

Перед отправкой pull request выполните:

```bash
npm run verify
```

Если launcher не может сам найти установленный Pi, задайте `PI_RUNTIME_FINAL_CLI` и `PI_TYPESCRIPT_BIN` для локальных путей текущего окружения.

## Pull request

Опишите поведение, которое меняется, и приведите результат проверки. Сохраняйте native lifecycle, публичные API и fallback-поведение Pi.

## Рабочий процесс

Разделение публичных документов, приватных планов и результатов проверок описано в [docs/workflows.md](docs/workflows.md). Локальный planning-контур необязателен для внешних участников.
Перед PR также выполните `npm pack --dry-run` и `git diff --check`; проверьте отсутствие локальных данных в diff и составе пакета.
Новые сообщения коммитов следуют Conventional Commits: `type(scope): краткое описание`. Существенные согласованные архитектурные решения оформляются ADR; для небольшого исправления достаточно описания изменения и проверки.
