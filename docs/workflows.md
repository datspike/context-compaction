# Рабочий процесс

## Публичное и локальное

| Слой | Назначение |
|---|---|
| Git | Код, тесты, README, CONTRIBUTING и переносимые правила |
| `.task_files/` | Приватные планы, вопросы, решения владельца и handoff |
| `.runtime/` | Локальные результаты проверок, eval, снимки и логи |
| `AGENTS.local.md`, `.pi/` | Локальная маршрутизация, настройки и состояние инструментов |

Сырые сессии, идентификаторы личных разговоров, абсолютные локальные пути, конфиги провайдера и секреты не публикуются. Для публичных примеров отдельно готовят обезличенные фикстуры. `.gitignore` защищает локальные слои; явный список `files` в package.json ограничивает состав npm-пакета. Перед публикацией проверяется и diff, и фактический пакет.

## Перед новой работой

Прочитайте AGENTS.md, а при наличии — AGENTS.local.md. Для личной инициативы сначала откройте канонический `.task_files/INDEX.md`, затем указанные в нём brief и текущую карточку. Внешнему участнику этот приватный слой не требуется.

Индекс содержит задачи и необходимые зависимости, не перечень логов. Каждая карточка указывает результат, статус, зависимости, владельца, worktree, следующий шаг и критерий завершения. При создании, разделении или изменении карточки индекс обновляют в той же работе. Если карточки и индекс расходятся, сначала исправляют маршрутизацию.

| Статус | Что разрешено |
|---|---|
| `ready` | Выполнение в утверждённых границах после проверки владельца и среды |
| `deferred` | Выбор для планирования; не автоматическая реализация или модельный прогон |
| `planning` | Сбор фактов и подготовка решения без изменения продуктового кода |
| `awaiting_decision` | Ожидание конкретного решения владельца |
| `claimed` | Работа закреплена за указанными сессией и worktree |
| `handoff-required` | Владелец недоступен; нужен явный перенос ответственности |
| `done`, `reference` | Проверенный итог либо материал для зависимой работы |

## Выбор следующей задачи и worktree

1. Проверьте ветку, рабочее дерево, локально известную базовую ветку и действующие claims. Отсутствие внешней сверки отмечайте прямо.
2. Если используется Orca, прочитайте актуальный установленный гайд и проверьте worktree, терминалы и соседние сессии. На этой машине используйте `orca-ide`, не bare `orca`.
3. Выберите первую свободную `ready` с закрытыми зависимостями. Если таких нет, выберите свободную `deferred` для `planning` и назовите эту границу.
4. Для реализации создайте отдельный worktree через действующий механизм проекта и запишите claim в каноническом индексе и карточке. Для одного планирования кодовый worktree не нужен.
5. Один участок изменяет один исполнитель. Терминал только с shell, отсутствие PR или старая активность не освобождают существующий worktree.
6. При недоступном владельце запросите handoff; не снимайте claim по таймауту. Перед началом реализации перечитайте правила и карточку.

После compact/resume, смены worktree, handoff и изменения индекса повторяется проверка маршрута и владения. Общий приватный план остаётся в основном checkout, а не копируется в каждое рабочее дерево. `.worktreeinclude` передаёт только локальный указатель AGENTS.local.md.

## Исследование, решение и реализация

Выбирайте минимально достаточный маршрут: brief, исследование, проверка прототипа или карта зависимых вопросов. У каждой проверки отделяйте подтверждённый факт, гипотезу и неизвестное.

Согласованные решения, меняющие публичный контракт, зависимости или модель сессии, оформляются ADR в `docs/adr/NNNN-slug.md`: контекст, решение, альтернативы, последствия, нецели, проверка и статус. Пустые ADR/RFC не создаются. Обычная локальная правка не требует архитектурного документа.

Модельный eval запускается только после определения данных, вариантов, версий, критериев и бюджета. Для фоновых прогонов сохраняйте проверяемые квитанции фактической модели, thinking и usage; используйте `eval-session-marker`, если этот skill установлен. Не сравнивайте заодно изменение модели и изменение compact без отдельного контрольного опыта.

## Проверка и завершение

```bash
npm run verify
npm pack --dry-run
git diff --check
```

`verify` запускает проверку типов и тесты через существующий launcher установленного Pi. Отдельный фиктивный lint не добавляется. Состав пакета сверяется с публичным списком файлов, отсутствие личных данных проверяется отдельно от успешности тестов.

Итог связывает требование, изменение, проверку и результат. Для крупной реализации нужен независимое ревью; обычная документационная подготовка не требует модельной кампании. Сообщения новых коммитов следуют Conventional Commits. Коммит, merge, push и PR выполняются только в границах конкретного поручения, а не потому, что появился план.

## Хранение и обслуживание

Архивирование плана не равно удалению: сначала сверяют статус, итог, ссылки и зависимости, затем переносят весь контур и обновляют индекс. Канонические документы и свидетельства сохраняют.

Удалять можно только доказанно временные или воспроизводимые материалы, не занятые живым процессом. На логи и снимки, упомянутые в итоговой квитанции, это правило не распространяется. Личные данные не коммитят с расчётом удалить их позднее.

CI, автоматизацию релизов, отдельные линтеры и дополнительные публичные документы добавляют по реальной потребности; незавершённые предложения остаются в приватном плане.
