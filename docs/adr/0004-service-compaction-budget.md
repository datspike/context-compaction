# ADR-0004: Отдельный бюджет и явный исход служебного compact

Статус: принято для реализации. Решение владельца от 2026-10-16: сохранить обычный режим 256K/272K; разрешить больший вход только служебному compact в подтверждённом окне точной модели и маршрута. Дополняет ADR-0003, не заменяя штатный pipeline Pi.

## Контекст

Окно обычного разговора не обязательно совпадает с физическим окном модели. Добавление задачи сводки и резерва выхода к истории около мягкого порога может превысить 272K. Изменение локального `contextWindow` само по себе не переключает серверный режим. Оценка всего сериализованного запроса через число символов смешивает текст, шифротекст и отдельный предел размера запроса.

Стандартный генератор также нуждается в защите актуальности после ожиданий: смена модели в Pi не гарантирует отмену уже выполняющегося compact. Возврат `undefined` после ошибки позволяет SDK запустить другой суммаризатор, скрывая дополнительную попытку.

## Решение

### Окна и источник возможности

Обычная policy и её порог не меняются. Служебная операция использует отдельную возможность точной пары provider/model и точного `baseUrl`. По умолчанию источник — текущая registry-декларация, а не увеличенное session-local окно. При намеренно заниженном registry оператор может задать `contextCompaction.compactCapabilities`: массив записей `provider`, `model`, `baseUrl`, `contextWindow`, `source`, необязательный `outputLimitEnforced`. Указание маршрута и непустого источника обязательно; неоднозначные дубликаты отклоняются. Настройка не изменяет ModelRegistry и не включает скрытый сетевой опрос.

`outputLimitEnforced` по умолчанию false. Без подтверждения соблюдения выходного ограничения резервируется объявленный максимум выхода модели, даже если запрошено меньше. Неизвестный максимум не заменяется оптимистичным числом. Подтверждение применимо только к указанному маршруту. Настройка не разрешает увеличивать обычное окно или считать все модели миллионными.

### Один расчёт, две точки проверки

Предварительная и окончательная проверки используют один предметный расчёт. Его входы: возможность с источником, оценка исходного входа с происхождением, добавочная задача, запрошенный выход, максимум выхода модели, запас и отдельно размер сериализации. Его результат содержит допуск либо причину отказа и составляющие бюджета. Предварительный допуск не заменяет окончательный. Стандартный служебный генератор тоже проверяет фактически сериализованный payload в `onPayload` перед сетью и сохраняет исходный отказ, если SDK превращает исключение обработчика в ошибочный ответ.

`encrypted_content` сохраняется в настоящем запросе, но не пересчитывается в обычные текстовые токены через длину шифротекста. Происхождение оценки явно: наблюдённый usage либо оценка; оценка не называется точным измерением. Предел сериализации проверяется независимо. Неподтверждённый кэш не уменьшает резерв.

Native-запрос по-прежнему строится штатными context/provider hooks. Делегирующая обёртка принудительно выбирает SSE только для собственного служебного запроса, оставляя обычный транспорт неизменным. Окончательный guard после поздних обработчиков проверяет структуру, принадлежность операции, неизменность допустимого запроса и бюджет до сети.

### Исходы и стандартная генерация

Неподдержанный путь, отказ до сети, завершённый неверный ответ, отмена, потеря контекста и неизвестный сетевой исход различаются. Существующий контроллер владеет разрешённым переходом на стандартный путь; ошибка стандартного генератора не разрешает SDK незаметно вызвать ещё один суммаризатор. Отмена, потеря контекста и неизвестный исход не запускают следующую попытку. Native-ответ SDK с `stopReason: error` также отменяет compact: диагностический класс не доказывает завершённый отказ провайдера. Разрешённое автоматическое продолжение выдаётся только в `agent_before_settle`, после проверки реально сохранённой границы, а не вместе с ещё изменяемыми черновиками `turn_end`.

`russianCompaction(event, ctx, options?)` сохраняет существующие аргументы. Необязательные параметры: `model` для служебного определения модели без смены активной модели; `capability` для явно подтверждённой служебной возможности; `isCurrent` для дополнительной проверки владельца; `onFailure` для предметной диагностики. Допустимый результат — `{ compaction }`; отказ — `{ cancel: true }`. Без модели запрос не отправляется. Перед каждым запросом, после каждого ожидания и перед возвратом результата проверяются signal, исходные session/tree/model/route и дополнительное владение. Для разрезанного хода (`split-turn`) это исключает второй запрос после утраты актуальности первого. Checkpoint-операция сохраняет идентичность provider/model/api/baseUrl; проверяет её после ожидания восстановления окна и перед follow-up. Внешние model/session/tree/fork transitions отменяют её, собственный переход размера окна той же модели не отменяет. Рабочие инструменты не выполняются; автоматические provider retries выключены. `/tree` этим решением не перерабатывается.

Подтверждение успеха остаётся за сохранённой границей. `firstKeptEntryId`, свежий хвост, происхождение данных, исходная причина автоматического compact и единственность checkpoint-продолжения не меняются. Прежний usage допустим после собственной очистки только при доказанном совпадении эффективного prefix и идентичности session/model/route/system/tools; иначе индикатор обозначает неопределённость, а не мнимое освобождение окна.

## Внутренние границы реализации

Расчёт и проверка capability выделяются в небольшой предметный `compact-budget.ts`, поскольку один и тот же расчёт нужен до и после сборки запроса. Он не вводит второй converter или универсальную машину состояний. `language.ts` читает необязательную настройку, сохраняя прежние значения по умолчанию. Стандартный генератор отвечает за актуальность собственного результата; native-контроллер — за полный жизненный цикл, окончательный запрос, сохранение и продолжение. Общие интерфейсы и интеграция принадлежат основному исполнителю.

## Альтернативы и последствия

Снятие защиты, удаление шифротекста из запроса, произвольный коэффициент и глобальная подмена окна отвергнуты: они не доказывают безопасный допуск. Уменьшение каталога может быть полезно позже, но не исправляет разделение окон. Неизвестная или действительно малая возможность даёт явный безопасный отказ либо разрешённый стандартный путь, а не скрытое расширение окна.

Большой служебный вход может пересечь ценовой порог провайдера. Это разрешено владельцем только для compact, не для обычного разговора; факт сохранённого prefix не обещает cache hit. Консервативный резерв может отклонить запрос, который сервер фактически смог бы выполнить, но не создаёт оптимистичного допуска на неподтверждённом выходном ограничении.

## Проверка

Немодельно проверяются четыре входа, разделение registry/session/service, точное совпадение маршрута, неизвестные значения, состав бюджета, независимый предел сериализации, поздняя подмена, SSE только для служебного запроса, split-turn и отмена/смена контекста после каждого ожидания. Дополнительно — сохранённая boundary, исходный хвост, отсутствие скрытой цепочки и единственное продолжение. Живая приёмка проверяет характерный вход около мягкого порога через точный маршрут и сохранение пользовательского результата; миллионный стресс-тест не требуется. Смысловая приёмка сохраняет решения, ограничения, причины и границы источников. README обновляется вместе с реализацией.

Ограничение сериализации имеет отдельный исход `request-too-large` в обоих путях, а не маскируется под `insufficient-window`. Квитанция окончательного native guard описывает фактический payload после штатных преобразований, включая схему ответа и поздние объявления инструментов. Сохранённая граница считается нашей только при совпадении `summary`, `firstKeptEntryId` и принадлежащих операции `details`; чужие дополнительные метаданные допустимы. Ожидающий пользовательский ввод после восстановления окна подавляет старое checkpoint-продолжение.
