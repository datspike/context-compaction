# ADR-0003: Restart-safe append через штатный ход Pi

Статус: принято для реализации. Основание — проверенный прототип и решение владельца от 2026-10-15 перевести все штатные входы compact: ручной `/compact`, checkpoint, threshold и overflow. Core Pi не меняется.

## Контекст

Прежний append использует сохранённый в памяти последний запрос. После перезапуска такого снимка нет. Его восстановление из JSONL не повторяет преобразования текущих расширений и не доказывает актуальность system/tools.

Служебный пользовательский ход проходит штатную сборку Pi и позволяет получить актуальный запрос без копирования pipeline. Проверенный прототип применяет сводку через публичные записи `compaction` и `context_edit` на границе хода. Десять немодельных сценариев и живой перезапуск подтвердили механизм. Это не доказательство попадания в кэш.

## Решение

У расширения один контроллер операции append: подготовленная Pi граница, исходная сессия и ветка, модель, служебный запрос, проверка payload, проверка ответа и подтверждение сохранённой сводки. В памяти хранится только состояние текущей операции; prompt/payload на диск не записываются.

Ручной compact сначала передаёт операцию контроллеру. Исходный вызов Pi отменяется, освобождая блокировку; затем служебный ход запускается только в исходной неизменённой сессии. Checkpoint связывает продолжение с подтверждённым применением, а не с callback отменённой подготовки. Контроллер не подделывает события или результат исходного `AgentSession.compact()`.

При автоматическом compact служебный запрос ставится в очередь текущего хода. Его исходные преобразования начала хода сохраняются, а контекст и payload проходят штатные обработчики снова. Overflow с `willRetry` продолжает исходную работу после применения границы; threshold не создаёт лишнего обычного ответа. Повторное восстановление одного и того же сбойного хода не запускается.

При допустимом отказе native-ответа на `overflow` стандартная русская сводка использует исходную подготовку и общий `russianCompaction()`. Она предлагается на `turn_end` вместе с очисткой служебного хода; ручной `ctx.compact()` не подменяет исходные причину и намерение продолжить работу. Если ответ с ошибкой завершил низкоуровневый цикл Pi, `agent_before_settle` продолжает работу только после подтверждения сохранённой границы. Если продолжение уже началось через `turn_end`, второй запрос не запускается. Отмена контролирует запрос сводки через сигнал действующего хода; перед применением повторно проверяются источник, сессия, модель и владение провайдером.

Делегирующая обёртка текущего провайдера сохраняет конвертер, авторизацию и обычные запросы. Внутри `onPayload` она ждёт всю штатную цепочку обработчиков, затем проверяет окончательный payload. Префикс, модель, cache key, `tool_choice` и формат ответа проверяются после всей цепочки; их подмена отклоняется до сети. Окончательные tools и параметр `include` принадлежат штатной цепочке преобразований: например, веб-поиск добавляет native declaration и запрашивает источники ответа. Эти поля не сравниваются с промежуточным состоянием до поздних обработчиков; проверяется их форма, а в провайдер передаётся окончательное значение без замены. Запрет исполнения остаётся обязательным: `tool_choice: none` и отклонение любых tool calls. Расширение проверяет владение регистрацией; при снятии своей обёртки не удаляет чужую замену.

Ответ проходит существующий валидатор структуры и происхождения фактов. Все рабочие tool calls блокируются. Публичные записи на границе хода сохраняют исходный `firstKeptEntryId`, исключают служебные сообщения и добавляют аудит/карточку только после проверки. Продолжение видит исходный свежий хвост, а не JSON ответа compact.

Отказы до отправки, неподдерживаемые провайдеры и нехватка окна используют существующий безопасный стандартный путь. Отмена, потеря сессии/ветки и неизвестный исход не запускают незаметный повтор. Невалидный завершённый ответ можно передать стандартному compact только после исключения служебных сообщений и освобождения текущего хода.

Для моделей с `supportsMidConvoEffort` адаптер Responses добавляет после текста задачи один `configuration_update` с уровнем reasoning. Расширение распознаёт этот штатный завершающий элемент, сохраняет его без изменений и проверяет текст задачи перед ним. Лишние элементы и позднее изменение конфигурации не допускаются; окончательная проверка payload остаётся строгой.

## Наблюдаемость и совместимость

После подтверждённого применения расширение добавляет постоянную карточку с окончательным результатом. Техническая отмена подготовки не считается ошибкой checkpoint или успехом append. Изолированная проверка Pi `1.3.0` подтвердила карточку, но выявила ограничение отображения: исходная отмена и служебные сообщения могут оставаться видимыми в ленте после удаления из модельной проекции. Полную перерисовку нельзя считать подтверждённой; понятность этого поведения ещё требует оценки при приёмке.

Прямой внешний вызов `AgentSession.compact()` всё ещё принадлежит Pi: при передаче управления он сообщает об отмене. Новая операция не меняет этот SDK-контракт. Штатные потребители расширения координируются через контроллер; эта граница должна быть описана в README и проверена отдельно от конечного состояния TUI.

Сохраняются режимы окна, языковые настройки, file hints, формат аудита и существующие карточки. Незавершённые изменения других веток автоматически не переносятся. Non-structured providers и подтверждение экономии не входят в решение.

## Проверка

Проверить поставляемое расширение, а не только прототип: все четыре входа; успешный и split-turn compact; ошибки формата/происхождения фактов; запрет нескольких инструментов; позднюю замену payload; отмену, смену модели/сессии/ветки и повторный compact; владение провайдером и обычные запросы после снятия обёртки.

Живая приёмка: завершить процесс, открыть ту же тестовую сессию, сразу выполнить compact и проверить содержательное продолжение на стандартной модели. Отдельно проверить настоящий TUI и текущий набор расширений в изоляции. Каждая фоновая модельная проверка имеет квитанцию model/thinking/usage. Сохранение исходных JSONL, свежего хвоста и отсутствие служебных сообщений проверяются независимо от статуса успеха.
