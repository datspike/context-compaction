# context-compaction

## Установка

Для установки из публичного Git-репозитория выполните:

```bash
pi install git:github.com/datspike/context-compaction
```

Для локальной разработки и проверки из рабочего дерева выполните:

```bash
pi install -l .
```

Базовая интеграция проверена на Pi `0.87.1`, текущие SDK-тесты и изолированный TUI — на `1.3.0`. Расширение не меняет ядро Pi.
Расширение задаёт окно сессии через публичный `pi.setModel()`, регистрирует `checkpoint_compact_continue` и команду `/context`. Подготовка автоматического сжатия остаётся у Pi; расширение подставляет свою сводку в `session_before_compact`. Оно же ведёт строку работы: стадию запроса, скорость генерации и стадию compact.

## Режимы

```text
/context status
/context economy
/context long-once
/context long-chat
/context off
```

- Базовая возможность и окно `economy` определяются по валидному `contextWindow` точной пары `(provider, id)` из `ctx.modelRegistry`.
- `economy`: применяет `min(272000, declared capability)`. Для окна 272K встроенный механизм Pi с обычным резервом 16K начинает сжатие примерно на 256K.
- При явном выборе `long-once` или `long-chat` расширение может включить session-local override до `600000`, если точная registry-запись уже содержит capability не меньше `272000` и действующие для всего запроса `cost.tiers` с порогом не ниже этого окна. Это общий сигнал для разных провайдеров, а не список моделей или провайдеров.
- Переопределение окна сессии не изменяет `models-store.json`, `models.json` или `ctx.modelRegistry`; оно применяется только через публичный `pi.setModel()` к текущей сессии и показывается как `source=session-override`. Повышенный pricing tier модели при этом остаётся ответственностью явного выбора long-режима.
- `long-once`: применяет `min(372000, effective capability)` и после **успешного** сжатия возвращается в `economy`.
- `long-chat`: применяет `min(600000, effective capability)` и сохраняется после сжатия и возобновления сессии.
- `off`: возвращает окно из реестра и отключает только мягкое ограничение расширения. Он не отключает автоматическое сжатие и восстановление после переполнения Pi: публичного API для отключения этих механизмов нет.
- Если registry-запись не даёт точного long-tier сигнала, long-режим отклоняется, даже когда объявленное окно больше 272K, а расширение оставляет `economy`.
При изменении метаданных через `pi.setModel()` расширение сохраняет текущий уровень рассуждений. Если модель не принимает новое окно, расширение пытается восстановить прежнюю модель. При подтверждённом восстановлении сохраняется прежний режим; если восстановление не подтверждено, показываются фактическое окно и `source=fallback`, а для повторной попытки нужно выбрать `economy`.

Строка состояния:

```text
ctx <tokens>/<window> <percent>% · compact@<threshold|off> · <mode>
```

Порог в строке состояния показывает ожидаемую границу встроенного сжатия Pi при стандартном резерве 16K. Это не отдельное правило расширения.

## Контрольная точка и сжатие контекста

`checkpoint_compact_continue` создаёт `manual-pending`; `ctx.compact()` запускается только на `agent_settled`, когда `ctx.isIdle()`. При ручном сжатии расширение передаёт структурированный журнал как дополнительные инструкции.

Успех compact подтверждает `session_compact`, а продолжение запускается из `ctx.compact().onComplete` после снятия блокировки Pi. Append и стандартная сводка идут одним путём: обе возвращаются из того же хука `session_before_compact`.

Перед продолжением проверяются ветка и сессия, идентичность модели, API и маршрута, последнее настоящее сообщение пользователя и состояние `pi-codex-goal`. Смена модели или переход к другой сессии, развилке либо ветке отменяет старое продолжение; собственное восстановление размера окна той же модели его не отменяет. Новый ожидающий ввод после восстановления окна тоже подавляет старое продолжение. Сохранённая граница должна совпадать с подготовленной сводкой, `firstKeptEntryId` и принадлежащими операции метаданными: одного идентификатора операции недостаточно. `sendUserMessage()` вызывается не более одного раза. Его публичный API не возвращает квитанцию постановки в очередь, поэтому журнал фиксирует вызов, а не гарантированную доставку; неизвестный исход не повторяется автоматически.

Порог и восстановление после переполнения остаются в ведении Pi. После успешного сжатия `long-once` возвращается в `economy`.

## Язык сводок

Расширение оставляет сжатие и сводку ветки в ведении Pi. В `ru` оно подставляет русские сводки через `session_before_compact` и `session_before_tree`; в `en` не подменяет их, и Pi использует штатные английские инструкции и формат. Для английского режима задайте в глобальном `<каталог Pi>/settings.json`:

```json
{ "contextCompaction": { "summaryLanguage": "en" } }
```

Допустимы только `ru` и `en`; без настройки используется `ru`. Расширение читает настройку при загрузке из `PI_CODING_AGENT_DIR` или `~/.pi/agent`; после изменения перезапустите Pi или выполните `/reload`. Неверное значение отклоняется при загрузке, а не превращается незаметно в другой язык. Установщик `pi-opinionated` настраивает это поле вместе с языком профиля; расширение можно использовать и отдельно.

При `en` обработчик `session_before_compact` сохраняет учёт операций, но не возвращает свою сводку; обработчик `session_before_tree` не регистрируется. `/context`, журнал аудита и `checkpoint_compact_continue` остаются доступны, а дополнительные инструкции ручной контрольной точки и сообщения расширения используют английский язык. Для новых английских сессий сводки compact, разрезанного хода и `/tree` создаёт штатный Pi; расширение не дублирует их алгоритм и не переводит сохранённые сводки.

При переключении существующей русской сессии штатный Pi может оставить текст прежней русской сводки в контексте разрезанного хода. Кроме того, при переходе с созданной расширением сводки на штатную Pi не переносит её накопительные `readFiles`/`modifiedFiles` из `details` в новый учёт файлов. Для полностью английской истории и непрерывного учёта файлов начните новую сессию. В `ru` расширение сохраняет подготовку разрезанного хода и полный накопительный учёт в метаданных. При ошибке русской генерации расширение явно отменяет compact, а не передаёт его скрытому штатному суммаризатору. Прежние метаданные и исходная история сохраняются.

### Cache-aware append compact

В русском режиме append compact включён по умолчанию для поддержанного `openai-responses`. Его можно отключить в глобальном `<каталог Pi>/settings.json`:

```json
{ "contextCompaction": { "summaryLanguage": "ru", "appendCompaction": false } }
```

Режим можно переключить только для текущего окна Pi, не трогая настройки и другие сессии:

```text
/context append on
/context append off
/context append status
```

Выбор живёт в памяти процесса и сбрасывается при `/new`, смене или перезагрузке сессии; без выбора действует `appendCompaction` из настроек. Строка состояния показывает режим: ` · append on` или ` · append off`, со звёздочкой, если он переопределён в этом окне.

Append — отдельный запрос к провайдеру, продолжающий последний рабочий запрос этого процесса (ADR 0007). Пока append включён, обёртка провайдера в реестре Pi держит в памяти последний отправленный рабочий запрос: модель, контекст, опции и окончательный payload после всех `before_provider_request`. На диск prompt и payload не пишутся. Append берёт этот контекст, дописывает новые сообщения ветки и задачу сводки, проводит payload через ту же цепочку обработчиков и сравнивает его с захваченным: модель, `prompt_cache_key`, `instructions`, `tools` и каждый элемент прежнего `input`. При расхождении запрос в сеть не уходит.

Платная попытка разрешена только при тёплом кэше. Нужен завершённый рабочий запрос этой сессии с той же моделью и адресом провайдера; после него в ветке только новые сообщения или записи вне контекста модели; пауза меньше срока жизни кэша минус 15 секунд. Срок берётся из `promptCache` модели для уровня `cacheRetention`, иначе 300 секунд. Если условие не выполнено, сразу строится стандартный compact без платной попытки, а причина пишется в аудит: `no-sent-request`, `not-warmed`, `cache-expired`, `route-changed`, `context-changed`, `payload-mismatch` и другие. Поэтому после рестарта, `/new` или смены модели первый compact всегда стандартный.

Поддерживается `openai-responses` с поддержкой системных сообщений посреди истории. Английский режим и `/tree` append не используют. Запрос идёт с `toolChoice: "none"`, без `text.format` (Structured Outputs обнуляют кэш префикса) и с сигналом compact, поэтому Esc отменяет его вместе с compact. Инструменты остаются в payload ради совпадения префикса, но ответ с вызовом инструмента отклоняется.

Ответ — обычный текст со стандартными заголовками. Проверки те же, что у стандартной сводки: в истории нужен «## Цель», при разрезанном ходе после строки `===РАННЯЯ ЧАСТЬ ХОДА===` нужен «## Исходный запрос». Лишний разделитель не считается ошибкой: ответ делится по первому. Пустой ответ, обрезанный ответ и вызов инструмента отклоняются. Отклонённый завершённый текст получает одну попытку исправления в том же кэшированном префиксе. Если и она не прошла, стандартная сводка строится в том же хуке, и Pi получает один результат compact.

Совпадение чисел сводки с сохраняемым хвостом не отклоняет ответ, а записывается в квитанцию попытки как `tailMatch`: роль источника, индекс сообщения, `number` или `ngram`, без самого текста. На 298 принятых сводках такие совпадения почти всегда были повторами итогов тестов, версий и бюджета.

Во время compact строка работы показывает `Compact: append по кэшу последнего запроса` или `Compact: стандартная сводка` и время с начала. Обработчики рабочего запроса, которые вызываются и для append, эту метку не перебивают.

После сохранённого compact появляется постоянная карточка `context-compaction-card`, не попадающая в контекст модели. Например: `◆ append compact · cache hit 92% · 258.8k → summary ~4.1k · 12.3 s · $0.0208`; при fallback: `◆ standard compact · append fallback (cache-expired) · …`. Ctrl+O раскрывает триггер, модель, cache read/input, время и стоимость обеих частей. Размер summary приблизительный и не включает сохранённый хвост. Карточка хранит числа и имена, не prompt или payload.

`context-compaction-append` версии 3 сохраняет outcome, duration, usage, cache status, `repairAttempts`, безопасный `appendAttempt` с фазами `preflight`, `provider`, `parse`, `apply` и `cacheCheck`. Это сверка с последним отправленным запросом: был ли захват и завершился ли он, пауза, срок кэша и его источник, совпадение сессии, провайдера, модели и адреса, наличие `prompt_cache_key`, число элементов `input` и usage прошлого запроса. При расхождении payload попытка содержит индекс первого различающегося элемента и имена полей, без содержимого. Отклонённая попытка содержит `validationGuard` и форму ответа `shape` без текста. Сам отклонённый ответ сохраняется отдельной записью `context-compaction-append-reply` вне контекста модели: номер попытки, guard, `tailMatch`, `stopReason` и текст. При переходе на стандартный путь расход append и стандартного compact учитывается раздельно; отказ стандартного пути пишет `context-compaction-standard` с причиной.

Попадание в кэш и экономия не следуют из успешного append. Их надо подтверждать фактическими usage и задержкой при правильном продолжении; `cacheRead=0` не доказывает потерю кэша после рестарта. Объявленные 272K нельзя расширять до 1M по одному pricing tier или виртуальному окну.

### Служебное окно и бюджет

Обычный режим `economy` сохраняет окно до 272K и мягкий порог около 256K. Окно служебного compact рассчитывается отдельно: оно не меняет registry, модель обычного разговора или её ценовую политику. По умолчанию используется объявление точной registry-модели, а не её временное session-local окно.

Если маршрут действительно поддерживает большее окно, оператор может задать `contextCompaction.compactCapabilities` — массив объектов с обязательными `provider`, `model`, `baseUrl`, `contextWindow` и `source`. Совпадение всех трёх полей маршрута должно быть точным; `contextWindow` — положительное целое, `source` — непустое описание подтверждения. Неизвестные поля, дубликаты маршрутов и неверные значения отклоняются при загрузке. Это объявление проверенной возможности, а не автоматическое обнаружение: чужой маршрут, pricing tier или документация другой модели не подтверждают его.

Дополнительное `outputLimitEnforced: true` допустимо только при подтверждённом соблюдении запрошенного ограничения выхода всей цепочкой провайдера и прокси. Без этого подтверждения резервируется полный `maxTokens` модели, даже если запрос просит короткую сводку; запрошенный выход при этом не увеличивается.

Предварительный и окончательный допуск используют один расчёт: оценка входа + задача сводки + выходной резерв + запас 4096 токенов должны помещаться в служебное окно. Окончательная проверка выполняется после поздних преобразований payload, до сети. Отдельно проверяется предел 16 MiB сериализованного запроса. Значения `encrypted_content` не пересчитываются как обычный текст и не удаляются из настоящего запроса; видимая оценка SDK остаётся оценкой, а не точным tokenizer usage.

Недостаточное или неизвестное окно, слишком большой запрос, отмена и ошибка результата имеют явные исходы. Разрешённый стандартный русский путь тоже проходит служебный бюджет; его отказ отменяет compact без следующего скрытого суммаризатора. После неизвестного сетевого исхода автоматической следующей попытки нет. Любой append-ответ SDK с `stopReason: error` отменяет compact: его строка ошибки не доказывает, что провайдер отклонил запрос до выполнения. Стандартный резервный путь остаётся для допустимых отказов до сети и завершённого невалидного текста. Он также проверяет фактический сериализованный запрос в `onPayload` перед сетью; отказ не скрывается, даже если SDK превратит исключение обработчика в ошибочный ответ. Оба пути различают `request-too-large` и `insufficient-window`; окончательная бюджетная квитанция append описывает фактический запрос после всех преобразований. Смена сессии, ветки, модели или маршрута не разрешает применить старую сводку.

### Файловые наводки

Смысловая часть сводки сохраняет цель, решения, ограничения, критерии завершения и достаточности и незавершённую работу. Важные для продолжения точные пути должны оставаться в этом тексте. Расширение не обрезает его ради ограничения файлового списка.

В русском режиме вместо полного перечня файлов добавляется блок `<file-hints>` длиной не более 6000 символов JavaScript (`String.length`, не токенов). Он содержит до 24 точных наводок, сгруппированных по папкам: сначала пути, упомянутые в смысловом тексте, затем недавно затронутые прямыми вызовами `read`, `write` и `edit`. До восьми групп показывают размер остальной истории. Корни разных рабочих деревьев не объединяются, длинные пути не обрезаются, а имена экранируются как JSON-строки.

Полные списки остаются в `details.readFiles` и `details.modifiedFiles` каждой созданной расширением записи. Это журнал наблюдавшихся обращений, а не текущий Git diff: он не доказывает успешность операции и не охватывает все изменения через командную оболочку, составные инструменты или другие процессы. Наводки не являются списком обязательных повторных чтений.

При следующем сжатии прежние файловые блоки убираются из входных сводок; смысловой текст, пользовательские сообщения и результаты инструментов не сокращаются этой обработкой. Блоки внутри ограждённых примеров кода и незавершённые файловые блоки сохраняются. Строки внутри завершённого файлового блока считаются данными журнала: в старом формате имена файлов не экранировались и могут напоминать разметку. Если имя совпадает с закрывающим тегом, граница блока сверяется с точными списками в метаданных. Без этих списков неоднозначную границу старого формата надёжно восстановить нельзя. Для `/tree` очистка выполняется до отбора истории по размеру, а исходные записи и их метаданные не меняются.

Для возвращения к прежним решениям используйте доступный поиск истории, например `session_search`/`session_get`, если они установлены. Полный файловый журнал можно прочитать в `details` соответствующей записи JSONL; расширение не добавляет новый поисковый инструмент и не требует Hermes. Старые сессии не переписываются. Английский режим и штатная генерация Pi остаются без изменений.

## Журнал сессии

Расширение добавляет записи типа `custom`, в которые данные только дописываются:

- `context-compaction-mode` с именованным режимом;
- `context-compaction-audit` версии 2: correlation, origin, reason, phase, tokens, window, threshold, mode, source, `willRetry` и зафиксированные идентификаторы сессии и ветки (`sessionId`, `tree`).
- `context-compaction-append` и `context-compaction-append-reply` с квитанциями append, описанными выше;
- `context-compaction-card` с карточкой результата compact.

Журнал аудита не содержит `summary`, текста сессии, содержимого вызовов инструментов, необработанных ошибок, данных авторизации и окружения, PID или путей. Старые `checkpoint-compact-session-threshold` только обнаруживаются, игнорируются и один раз показывают уведомление; они не переписываются.

## Проверка

```bash
# Выполняйте команду из корня репозитория
npm run verify
```

`verify` использует набор зависимостей текущего `pi` и проверяет типы локальным TypeScript из `devDependencies`. Если `pi` запускается через оболочку-обёртку, задайте `PI_RUNTIME_FINAL_CLI` для фактического исполняемого файла Pi; поиск пути не выполняется для другого `pi` в `PATH`.

## Для участников

Перед отправкой изменений запустите `npm run verify` и проверьте Git-установку из отдельного чистого каталога Pi. Не добавляйте `node_modules`, `.env`, локальные артефакты окружения и временные файлы. Изменения поведения должны опираться на публичные API Pi; закрытые обходы внутреннего runtime и подмена методов во время выполнения в проекте не принимаются.

Переносимый рабочий процесс и границы публичных/локальных данных: [docs/workflows.md](docs/workflows.md). Приватные планы и результаты модельных экспериментов не входят в Git и публикуемый пакет.
